# Публикация рабочего Apps Script

Подготовлен workflow [Production Apps Script](../.github/workflows/apps-script-production.yml)
и исполнитель [production-backend.cjs](../scripts/production-backend.cjs).
Это отдельный процесс от выпуска APK. Автозапуск при push/PR **не включён**.
Workflow пока существует в рабочей ветке `test`; для первого запуска нужен
согласованный перенос в `master`. Автоматизация отложена по решению пользователя;
рабочий сервер опубликован вручную через clasp, как описано ниже.

## Текущий рабочий сервер

14.11.2026 по подтверждению пользователя рабочее развёртывание обновлено через
clasp до **версии 27**, с сохранением deployment ID и URL из
`config/environments/production.json`. Опубликован локальный снимок серверных
исходников ветки `test`; слияние `master` и выпуск APK не выполнялись.
Резервная версия прежнего HEAD — **24**, прежняя опубликованная версия — **23**.
При первоначальных проверках потребовалось восстановление прежнего кода:
Google не сразу показывал созданные версии и обновлённое состояние deployment.
Последующая публикация и повторная независимая проверка чтения прошли успешно.

Схема десяти листов и единственный активный снабженец проверены через Sheets
connector, не через отключённый Sheets REST API OAuth-клиента clasp. После
публикации проверены hash неизменяемой версии, прежний URL, полный `full_sync`,
отдельный импорт настроек уведомлений, сотрудников, финансовых операций и визитов.
Новые визиты/начисления на рабочем стенде для тестирования не создавались:
атомарная запись через Advanced Sheets требует отдельной контролируемой проверки.
Токены Script Properties и расписания триггеров не изменялись; сами триггеры
могли исполняться по расписанию на новом HEAD.

Для следующей ручной публикации сначала проверить рабочие ID и свежие заголовки
через connector, скачать HEAD и сохранить отдельную неизменяемую backup-версию.
Публиковать только явно согласованный снимок, обновлять существующий deployment
и повторно проверять его версию/URL/контракт. Учитывать задержку видимости новых
версий: после неоднозначного ответа сначала сверить состояние, а не создавать
новые версии повторно. `Invoke-ProductionClasp.ps1` остаётся read-only; это не
универсальная команда публикации. Резервные исходники и отчёт локального выпуска
сохранены в игнорируемом `.codex/manual-production`, не в Git или публичных artifacts.

## Однократная настройка GitHub

В **Settings → Environments** создать `production-apps-script`:

1. Разрешить deployment только из ветки `master` (Selected branches and tags).
2. Добавить Required reviewers. Если выпускает один владелец, запрет self-review
   не включать: иначе он не сможет одобрить собственный запуск.
3. Добавить следующие **environment secrets**, не общие секреты всех веток.

| Secret | Содержимое |
| --- | --- |
| `PRODUCTION_CLASP_AUTH_JSON` | JSON авторизации Google в формате clasp: `tokens.default` с `client_id`, `client_secret`, `refresh_token` |
| `PRODUCTION_SYNC_TOKEN` | Рабочий `SYNC_TOKEN` из Script Properties, тот же, что использует приложение |

Авторизация Google уже сохранена локально в `%USERPROFILE%\.clasprc.json`.
Для CI достаточно трёх перечисленных полей из `tokens.default`; `access_token`,
`id_token`, другие пользователи и сроки действия не нужны. Значения не отправлять
в чат, Git, логи, issue или artifact. На runner access token обновляется через
OAuth refresh и хранится только в памяти процесса.

Это доступ от имени Google-пользователя, не отдельная серверная роль. Для
долгосрочной эксплуатации предпочтителен выделенный аккаунт с доступом только
к нужным ресурсам. Отзыв OAuth-доступа потребует повторной авторизации.
Токен должен разрешать Apps Script API и чтение рабочей таблицы через Sheets API
(подходящий Drive/Sheets scope); сами API должны быть включены для OAuth-проекта.
Недостаток прав приводит к остановке до загрузки исходников. Скрипт не включает
API и не выдаёт новые права самостоятельно.

в рабочий `employees!A3:G3` добавлен Денис: ID 2, `SUPPLY_OPERATOR`, активен;
`workStartDate` оставлена пустой, поскольку фактическая дата не указана.
Схема подготовлена; в исходниках сняты TEST-ограничения визитов, заработка и
синхронизации настроек. Сервер опубликован как версия 27; APK ещё не выпущен.
Перед следующим выпуском заново проверить заголовки,
сотрудника снабженца и полный сценарий синхронизации.

### Обязательные условия нового выпуска

- В рабочем `employees` должен быть ровно один активный `SUPPLY_OPERATOR`
  с непустым именем и уникальным положительным ID. Денис добавлен с ID 2;
  дату начала работы не выдумывать, тестовые финансовые операции не копировать.
  Preflight читает ограниченный реестр сотрудников и останавливает публикацию
  при отсутствии/неоднозначности снабженца. Имя и ID не захардкожены в production.
- Рабочая Room-БД не создаёт local-only профиль. Если на устройстве ещё нет
  однозначного снабженца, завершение 4-го этапа сначала пробует импорт сотрудников.
  Без подходящего сотрудника визит, деньги и дата миксеров не сохраняются.
- Для атомарного визита нужен Advanced Sheets v4 и разрешения Google у владельца
  web app. Новая зависимость в manifest сама не доказывает, что рабочий Cloud API
  включён и пользователь уже выдал все необходимые разрешения.
- Опубликовать сервер раньше зависимого APK. Старые APK не создают визиты и
  начисления снабженца; задним числом они автоматически не появятся. Проверить
  чтение и узкие запросы старого клиента на TEST перед рабочим выпуском.
- Проверить новый контракт на TEST, затем production preflight с `publish=false`.
  Реальную публикацию и APK выполнять только по отдельному подтверждению.

После согласованного слияния открыть **Actions → Production Apps Script → Run workflow**:

- Ветка workflow: `master`.
- `source_sha`: полный 40-символьный SHA коммита, уже вошедшего в `master`.
- `expected_version`: текущая опубликованная версия рабочего развёртывания.
  При настройке доступа 14.11.2026 это была **23**; перед запуском проверить актуальность.
- `publish`: **false**.

Workflow запускает тесты без секретов, затем protected job с секретами:

1. Проверяет чистый checkout выбранного SHA и его принадлежность `master`.
2. Собирает `.gs` и manifest только из этого checkout; Config получает
   `ENVIRONMENT=production`, рабочие ID и московский часовой пояс.
3. Проверяет существующий deployment, номер версии и неизменный URL.
4. Читает названия листов и строки заголовков через Sheets API. Ничего не создаёт
   и не переставляет. Требуются все листы и колонки из Config выбранного коммита.
   Кандидат с визитами также требует ровно одного активного снабженца и корректных
   уникальных ID сотрудников; реестр читается только для проверки, без записи.
5. Читает код опубликованной версии и текущего HEAD. Сравнивает webapp access
   и явные OAuth scopes, не допускает их скрытой смены.
6. Проверяет текущий API read-only запросом станций с рабочим sync-токеном.

При `publish=false` нет PUT/POST изменения Apps Script, создания версий,
записи в таблицу или запуска триггеров. Запрос OAuth POST только обновляет
токен авторизации. Нужные новые листы/колонки рабочего стенда ещё должны быть
подготовлены отдельной задачей; текущий кандидат может не пройти этот preflight.

## Публикация

После успешного preflight запустить с тем же SHA и `publish=true`, проверить
ожидаемую версию и одобрить deployment. Все проверки выполняются заново.

- Создаётся отдельная неизменяемая версия резервной копии текущего HEAD,
  включая неопубликованные изменения редактора. Прежняя опубликованная версия
  уже существует и также остаётся доступной.
- Загружается кандидат, проверяется hash кода, создаётся его версия.
- Обновляется **только существующий deployment**, URL не меняется.
- `full_sync` проверяется по независимому JSON-контракту. Чтение повторяется
  до трёх раз с короткой паузой на распространение новой версии.
- Artifact `deployment-report.json` содержит SHA, версии, hashes и результат.
  Исходники резервных копий, ответы с бизнес-данными и авторизация не публикуются
  как artifacts. Резервные исходники доступны через version history Google.

Используется официальный Apps Script REST API с авторизацией clasp, без
зависимости от парсинга текстового вывода CLI. `Invoke-ProductionClasp.ps1`
остаётся отдельной read-only командой для локальной диагностики.

## Ошибки и откат

При ошибке после попытки загрузки workflow проверяет фактическое состояние
Google: запрос мог примениться до сетевого таймаута. Если код и deployment
по-прежнему принадлежат этой операции, восстанавливает предыдущий HEAD
и прежнюю опубликованную версию. Сам запуск остаётся неуспешным.

Если замечена посторонняя правка, автоматический откат отказывается её
перетирать: результат `rollback-needs-attention`, требуется ручная проверка.
GitHub concurrency исключает два workflow выпуска одновременно, но **не**
защищает от ручной правки в Google. На время выпуска не редактировать проект
и не публиковать его другим инструментом. Apps Script API не предоставляет
единую транзакцию кода/версии/deployment; остаётся окно гонки после проверок.

Триггеры используют HEAD уже после загрузки кода, не после публикации `/exec`.
Workflow не переустанавливает/удаляет/запускает триггеры, но они могут сработать
по своему расписанию на новом HEAD. Откат кода не отменяет сделанные ими записи
в таблицу или внешние эффекты. Смена схемы, новых разрешений и алгоритмов
начислений требует отдельного плана совместимости, не только smoke-проверки.

При аварии runner/принудительной остановке автоматический откат не гарантирован.
Сохранённые Google-версии позволяют восстановиться отдельно; workflow не удаляет
предыдущие версии и не делает откат листов/данных.

## Проверки реализации

`scripts/tests/production-backend.test.cjs` использует подставной API: проверяет
схему, версии/URL, отсутствие записи до preflight, публикацию, откат после ошибки,
таймаут после применённой записи, посторонние изменения и безопасные ошибки.
Это не реальная публикация в Google и не проверка Secrets/Environment на GitHub.
Проверки подключения/публикации в CI нужно выполнить после слияния и настройки.

Локальная подготовка 14.11.2026: общий Node-набор — 102 успешные проверки и
один прежний TODO удаления каталога; на эмуляторе — 24 проверки визитов,
финансовой синхронизации, настроек уведомлений и экранов заработка. Среди них:
новая пустая БД с импортом серверного снабженца, отказ local-only профилю по
production-правилам, повтор и потеря ответа без второго начисления. Тесты
используют подставной API и локальные БД, не записывают операции в рабочую таблицу.
Это не заменяет успешный GitHub preflight и проверку нового развёртывания.

После успешного контролируемого выпуска можно отдельно добавить автозапуск
на изменения серверных файлов в `master`; сейчас его намеренно нет.

Официальные справочники: [Apps Script REST API](https://developers.google.com/apps-script/api/reference/rest),
[исполнение нового HEAD после updateContent](https://developers.google.com/apps-script/api/reference/rest/v1/projects/updateContent),
[защита GitHub Environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).
