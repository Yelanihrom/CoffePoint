# Модель данных

Локальная БД: `coffee_point.db`, Room schema version **38** на 10.11.2026.
Определение: [AppDatabase](../app/src/main/java/ru/coffeepoint/core/data/local/AppDatabase.kt).
Миграции: [DatabaseProvider](../app/src/main/java/ru/coffeepoint/core/data/local/DatabaseProvider.kt).

В Google Sheets используются одноимённые листы. Их точный порядок столбцов
зафиксирован в [Config.gs](../google-apps-script/Config.gs) и независимом
[JSON-контракте](../app/src/test/resources/contracts/sheet-schema.json).
Локальная Entity и строка Sheets не обязаны содержать одинаковые служебные поля.

## Таблицы

| Таблица / лист | Ключ | Что хранит | Связь |
| --- | --- | --- | --- |
| `coffee_station` | `id: Int` | Информация о станции, терминал, даты обслуживания, продажи, аренда | Основная запись станции |
| `station_inventory` | `stationId: Int` | Девять текущих остатков | Одна запись на станцию |
| `station_settings` | `stationId: Int` | Девять пар минимум/максимум | Одна запись на станцию |
| `supply_catalog` | `id: Int` | Вариант закупки, артикул, цена, ссылка, активность, приоритет | Несколько вариантов для одного `itemType` |
| `warehouse_stock` | `itemType: String` | Количество, минимум и максимум склада | Одна запись на тип позиции |
| `notification_settings` (Sheets; не Room) | `role: String` | Флаги уведомлений по ролям | Одна строка на MANAGER, OPERATOR, SUPPLY_OPERATOR; Android синхронизирует локальные SharedPreferences |
| `employees` | `id: Int` | Имя, роль, дата начала работы, активность | Сотрудник, а не выбранная роль устройства |
| `employee_station_assignments` | `id: String` | `employeeId`, `stationId`, период привязки | История ответственности за станцию |
| `employees_transactions` | `id: String` | Начисление или выплата сотруднику | Связь по `employeeId` |
| `station_service_visits` | `id: String` | История завершённых обслуживаний, Room и Sheets | `employeeId`, `stationId` |

Подраздел аналитики «История обслуживаний» читает `StationServiceVisitDao.observeHistory()`:
Room Flow с LEFT JOIN к станции и сотруднику. Сортировка по `julianday(completedAt)`
учитывает временную зону ISO-времени; pending-записи не исключаются. Это новая
выборка, не изменение таблиц или миграция Room. Удаление справочной записи не
скрывает историю: UI использует ID вместо отсутствующего имени.

Связи в этой таблице логические: текущие Entity не объявляют внешние ключи Room.
Нельзя считать, что удаление станции автоматически каскадно очищает все связанные
сотруднические записи.

## Настройки уведомлений в Sheets

Лист `notification_settings` (`gid=2005` на обоих стендах) содержит три строки и колонки:
`role`, `refillEnabled`, `criticalStockEnabled`, `warehouseEnabled`,
`mixersEnabled`, `liquidWasteContainerEnabled`, `brewUnitEnabled`, `exhaustEnabled`,
`expansionTankEnabled`, `coffeeGrinderEnabled`, `updatedAt`.
Флаги — настоящие boolean с checkbox-валидацией, не текст TRUE/FALSE.
Роль — естественный ключ без дополнительного UUID. Пустые/дублированные роли
и не-boolean значения недопустимы. Оператору доступна только заправка,
снабженцу — всё, кроме заправки. Остальные недоступные флаги равны false.
`updatedAt` отображается по Москве как `yyyy-MM-dd HH:mm:ss`, API — ISO UTC.
При ручной правке флажков нужно также менять время строки: onEdit-триггер
для этого не добавлен. Android читает все три роли и отправляет только
изменённые поля через connector. SharedPreferences хранят локальные флаги,
`{role}.pending.{option}`, `{role}.updatedAt` и `{role}.remoteUpdatedAt`.
Прежние локальные настройки без pending не выгружаются автоматически: первая
успешная загрузка заменяет их данными Sheets. Pending остаётся локальным и не
переносится в лист. Room-схема при подключении настроек не меняется.

## Остатки и типы позиций

В `station_inventory` остатки — отдельные поля, а в складе и каталоге тип
задаётся строкой `itemType`:

| Название | Код / имя поля | Настройки станции |
| --- | --- | --- |
| Стаканы | `cups` | `cupsMin`, `cupsMax` |
| Крышки | `lids` | `lidsMin`, `lidsMax` |
| Сахар | `sugar` | `sugarMin`, `sugarMax` |
| Мешалки | `stirrers` | `stirrersMin`, `stirrersMax` |
| Пакеты | `garbageBags` | `garbageBagsMin`, `garbageBagsMax` |
| Кофе | `coffee` | `coffeeMin`, `coffeeMax` |
| Молоко | `milk` | `milkMin`, `milkMax` |
| Шоколад | `chocolate` | `chocolateMin`, `chocolateMax` |
| Топпинг | `topping` | `toppingMin`, `toppingMax` |

Строка склада имеет серверные поля именно в таком порядке:

```text
itemType, quantity, minQuantity, maxQuantity, updatedAt
```

При изменении единиц измерения нужно согласованно менять значения станции,
склада, списания и закупки. Количество не всегда означает отдельные физические
штуки товара; единицы отображаются соответствующими моделями интерфейса.

## Станция и серверные продажи

На листе `coffee_station` подряд расположены:

```text
lastServiceDate, salesAfterService, salesUpdatedAt
```

`lastServiceDate` — дата последней заправки оператора. `salesAfterService` — целое
количество продаж после неё, формат ячейки должен быть числовым. `salesUpdatedAt`
— время серверного пересчёта. В текущей Room Entity `salesUpdatedAt` отдельно
не хранится. Время последнего импорта устройства хранится в Preferences.

Даты узлов обслуживания независимы: `mixersServiceDate`,
`liquidWasteContainerServiceDate`, `brewUnitServiceDate`,
`coffeeGrinderServiceDate`, `expansionTankServiceDate`, `exhaustServiceDate`.

## Локальные статусы

`isSynced`, `syncError`, `syncErrorType` и pending-флаги станции относятся к
локальной отправке. Их не нужно добавлять колонками в Google Sheets.
Смысл статусов и правила повторов: [синхронизация](synchronization.md).

`updatedAt` относится к последнему изменению записи. Это не время чтения
сервера и не время каждого повтора POST. Часть локальных дат хранится в
формате `dd.MM.yyyy`, а серверные timestamps — ISO-строками; преобразования
сосредоточены в connector. Сервер использует `Europe/Moscow`.

## Сотрудники и операции

`validFrom` и `validTo` у привязки определяют её действие в конкретный день.
Серверный расчёт учитывает обе границы включительно; пустой `validTo` — открытый
период. Пересечение назначений одной станции разным операторам за один день
вызывает ошибку ежедневного расчёта.

Операции `EARNING` и `PAYMENT` находятся в одной таблице. Сумма `amount` — целое
число рублей; знак для отображения и взаиморасчёта определяется типом операции.
Для автоматических начислений дата `operationDate` равна дню заработка в
00:00:00; `createdAt` отражает фактическое создание серверной записи.

Автоматическое начисление имеет детерминированный ID
`AUTO-EARNING-{employeeId}-{yyyy-MM-dd}`; выплата из Android — отдельный UUID.
Повторное начисление за тот же день не должно создавать новый случайный ID.

## Как менять схему

### Локальные визиты снабженца

Локальная запись `station_service_visits`: миграция 35 → 36
создаёт пустую таблицу и индексы по сотруднику/дате и станции/дате, не меняя
существующие данные. Поля: `id` (UUID визита), `employeeId`, `stationId`,
`completedAt`, `createdAt`, `updatedAt`, `isSynced`, `syncError`, `syncErrorType`.
Временные отметки сохраняются как ISO UTC. `completedAt` — фактическое завершение
4-го этапа, `createdAt` — будущее время создания на сервере; до ответа сервера
оно может быть `null`. Суммы в визите нет: деньги относятся к финансовой операции.

Завершение 4-го этапа ролью `SUPPLY_OPERATOR` создаёт визит
на единственного активного снабженца. В TEST доступен локальный Денис;
production допускает только серверный профиль (`isLocalOnly=false`). Визит, начисление
2000 рублей и pending-дата миксеров сохраняются одной Room-транзакцией. Без однозначного сотрудника
сохранение не выполняется. Управляющему визиты не создаются.
UUID завершения хранится в `SavedStateHandle` экрана. Повтор с тем же UUID
читает существующий визит, не меняя дату, время и сотрудника. Новое прохождение
может создать другой визит в тот же день. UUID восстанавливается вместе с
состоянием экрана Android; при потере навигационного состояния это не заменяет
полноценный журнал незавершённых сессий обслуживания.

Каждый новый визит создаёт `EARNING` с обычным UUID в `id`,
`sourceType=SUPPLY_SERVICE`, `sourceId=visitId`, `isLocalOnly=true`.
Ставка 2000 рублей задана в `SupplierServiceCompletionRepository`.
Дата операции равна времени завершения визита; история отображается по Москве.
Ранее локально записанные pending-визиты отправляются с прежними ID; при
подтверждении серверное начисление заменяет предварительную операцию по источнику, а не
добавляется рядом. Миграция 37 → 38 добавляет
`sourceType`, `sourceId`, `isLocalOnly` в `employees_transactions` и уникальный
индекс по источнику. Старые операции сохраняются, их источник остаётся `null`.
UUID предварительного начисления хранится в Room и отправляется как `earningId`.
Сервер ищет существующую операцию по `sourceType/sourceId`, сохраняет её прежний
UUID либо принимает присланный UUID для нового начисления. Если серверный и
локальный ID различаются, старый локальный ID удаляется в той же Room-транзакции
перед записью подтверждения; сумма не удваивается. Это также поддерживает старые
локальные `SUPPLY-EARNING-*`. Выплаты уже имеют обычные UUID и не меняются.
Автоматические начисления оператора сохраняют `AUTO-EARNING-{employeeId}-{date}`.
Предварительные начисления исключены из общего upsert и сохраняются при сверке.
`SupplierVisitSyncService` отправляет pending-визиты и атомарно применяет
серверную пару через `EmployeeDataImporter`: `isSynced=true`, `isLocalOnly=false`,
ошибки очищаются. До подтверждения сохраняются локальные значения и ошибки.
Отправка даты миксеров остаётся отдельным запросом. История визитов пока
доступна через инспектор БД, отдельного экрана нет.

11.11.2026 в тестовой Google-таблице подготовлен пустой лист
`station_service_visits` (`gid=2004`): `id`, `employeeId`, `stationId`,
`completedAt`, `createdAt`, `updatedAt`. Первая строка закреплена; UUID — текст.
Временные отметки визитов, финансовых операций, сотрудников и привязок хранятся
в Sheets как даты, с единым отображением `yyyy-MM-dd HH:mm:ss` по Москве.
Миллисекунды сохраняются в значении ячейки; API возвращает ISO UTC.
Дата начала работы и границы периодов остаются отдельными датами без времени.
Локальные `isSynced`, `syncError`, `syncErrorType` в лист не переносятся.
Денис добавлен в тестовый `employees` с ID 2, как в проверенной локальной TEST-БД.
В `employees_transactions` добавлены `sourceType`, `sourceId` после `updatedAt`;
старые данные и порядок прежних колонок сохранены. Серверный обработчик описан
в [контракте API](api-endpoints.md#визиты-снабженца).
Android загружает `stationServiceVisits`, подтверждает начисления по
`sourceType/sourceId` и отправляет выплаты с постоянным UUID.
14.11.2026 подготовлены рабочий лист визитов, лист настроек уведомлений и две
колонки источника в транзакциях. По отдельному подтверждению в рабочий реестр
добавлен активный Денис (ID 2, `SUPPLY_OPERATOR`), дата начала работы пустая.
Тестовые финансовые операции не переносились. Сервер опубликован как версия 27,
APK с этими изменениями ещё не выпущен;
см. [план публикации](production-backend.md).

### Локальный сотрудник для тестирования

Миграция 36 → 37 добавляет `employees.isLocalOnly` (по умолчанию `false`).
Только в тестовой сборке при открытии БД создаётся сотрудник «Денис»,
`SUPPLY_OPERATOR`, `isLocalOnly=true`, `isSynced=false`. ID выбирается свободным,
не меньше 2; существующий сотрудник с тем же именем и ролью не заменяется.
Дата начала работы пока пустая: фактическая дата не была указана пользователем.
Повторное открытие не создаёт дубль и не обновляет даты существующей записи.

Локальный сотрудник исключён из очереди отправки сотрудников. При импорте в TEST
совпадение ID/имени/роли снабженца позволяет принять серверную запись и снять
`isLocalOnly`; другое имя или роль отклоняются с откатом Room-транзакции.
Его локальные выплаты становятся доступными для отправки. Начисления остаются
предварительными до подтверждения визита. Признак `isLocalOnly` не передаётся
в Sheets. Рабочая сборка сама Дениса не создаёт и этот переход не разрешает.
Экран заработка выбирает первого активного `OPERATOR` для оператора, а
для снабженца — единственного активного `SUPPLY_OPERATOR`.
Кэш взаиморасчёта разделён по ролям. Выплаты Денису синхронизируются после
согласования сотрудника; непереданные операции не теряются при импорте.

### Порядок изменения

1. Согласовать поля, типы, ключи и поведение старых устройств.
2. Изменить Entity, DAO и Room-миграцию, увеличить `AppDatabase.version`.
3. Обновить модели, mapper и сетевые преобразования.
4. Добавить/переставить столбцы Sheets вместе с их данными. Одного изменения
   текста заголовка недостаточно для перемещения существующей колонки.
5. Обновить `Config.gs`, JSON-контракт, примеры ответов и тесты.
6. Проверить локальные тесты, затем опубликованный сервер.

Порядок полей Entity сам по себе не перестраивает существующую SQLite-таблицу.
В Room используются имена столбцов. Сейчас `exportSchema=false`, поэтому
версионированных экспортов схемы и полного набора тестов миграций нет.
