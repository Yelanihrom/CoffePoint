# Сборка и выпуск приложения

## Номер версии

Источник номера — [app/build.gradle.kts](../app/build.gradle.kts):

```kotlin
versionCode = 14
versionName = "1.0.14"
```

Это значения исходников на 20.10.2026. Для следующего выпуска `1.0.15` нужно
изменить их на `15` и `"1.0.15"` **до сборки**. Переименование APK, создание
тега или описание релиза не меняют версию внутри уже собранного файла.

`versionCode` увеличиваем для каждого распространяемого обновления, включая
тестовые сборки. `versionName` — видимая пользователю версия; тестовый пример:
`1.0.15-beta.1`.

## Перед сборкой

1. Проверить рабочую ветку, состав изменений и адрес Apps Script.
2. Обновить документацию, если менялись процессы, запросы или схема.
3. Прогнать локальный набор:

```powershell
.\scripts\Test-Api.ps1 -JavaHome 'D:\Android Studio\jbr'
```

После изменения сервера отдельно запустить проверку чтения живого развертывания
из [реестра API](api-endpoints.md). Наличие успешного локального теста не
подтверждает правильность Script Properties и публикации.

## Debug и release

Последние APK для ручного тестирования собирались как `debug`. Для сборки:

```powershell
$env:JAVA_HOME = 'D:\Android Studio\jbr'
.\gradlew.bat :app:assembleDebug
```

Результат: `app/build/outputs/apk/debug/app-debug.apk`.

При измерении размера после массовой замены изображений нужна чистая сборка:

```powershell
.\gradlew.bat :app:clean :app:assembleDebug
```

Для release используется `:app:assembleRelease`. Подпись берётся из локального
`release-signing.properties` со свойствами `storeFile`, `storePassword`,
`keyAlias`, `keyPassword`. Ключ хранится вне Git; файл настроек также игнорируется.
Результат подписанной release-сборки: `app/build/outputs/apk/release/app-release.apk`.

Ключ подписи нужно сохранять между выпусками. Debug и release с разными
ключами не устанавливаются друг поверх друга как одно обновление. До перехода
на постоянную release-подпись нужно учитывать уже установленные debug-сборки
и их неотправленные локальные данные.

Оптимизация кода release пока отключена (`isMinifyEnabled=false`);
R8/resource shrinking не входят в выполненную оптимизацию изображений.

## Изображения

17 растровых иконок в `drawable-nodpi` имеют размер 256×256 и формат WebP
с прозрачностью. Схема кнопок `grind_control_keypad` сохранена в 1448×1086,
WebP без потерь. В ссылках `R.drawable` расширение файла не используется.

Проверенная чистая debug-сборка после этих изменений уменьшилась с 42,7 до
24,4 МиБ. Это измерение конкретной сборки, а не гарантированный размер будущих
версий. Высокодетальные исходные PNG доступны в истории Git до замены ресурсов.

## GitHub Releases

1. Зафиксировать исходники выпуска коммитом и отправить его на GitHub.
2. На странице репозитория открыть **Code → Releases → Create a new release**.
3. Создать тег версии, например `v1.0.15`, на нужном коммите ветки `master`.
4. Указать название и реальные изменения выпуска.
5. Прикрепить соответствующий APK, например `CoffeePoint-1.0.15.apk`.
6. Для тестового выпуска из ветки `test` отметить **Set as a pre-release**.
7. Опубликовать и проверить, что файл доступен в разделе Assets.

Ветка двигается с новыми коммитами, тег фиксирует версию исходников. APK
не добавляем обычным файлом в Git: он прикрепляется к релизу.

GitHub не собирает APK автоматически только из-за коммита или нового тега.
CI для этого в текущем проекте не настроен. Пользователь скачивает APK из
Releases и устанавливает вручную; встроенного автообновления приложения нет.

## Apps Script выпускается отдельно

Для обновления кода HTTP API сохранить файлы в нужном проекте Google и выбрать
**Развернуть → Управление развертываниями → карандаш → Новая версия**.
Обновление существующего развертывания сохраняет URL. Если создан новый URL,
его нужно перенести в Android-конфиг и пересобрать приложение.

Триггеры работают с сохранённым кодом проекта; наличие нового кода в редакторе
само по себе не обновляет опубликованный versioned `/exec`. После изменения
имени или расписания триггера проверить установленный триггер отдельно.
