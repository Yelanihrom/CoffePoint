# Сборка и выпуск приложения

## Номер версии

Источник номера — [app/build.gradle.kts](../app/build.gradle.kts):

<!-- generated:app-version:start -->
```kotlin
versionCode = 15
versionName = "1.0.15"
```
<!-- generated:app-version:end -->

Блок выше генерируется из Gradle командой `node scripts/docs.cjs --write`.
Не редактируйте его вручную. Переименование APK, создание тега или описание
релиза не меняют версию внутри уже собранного файла: после изменения номера
в Gradle APK нужно пересобрать.

`versionCode` увеличиваем для каждого распространяемого обновления, включая
тестовые сборки. `versionName` — видимая пользователю версия; для тестовой
версии можно добавить суффикс `-beta.1`.

## Рабочие ветки

Все новые изменения сначала вносим и отправляем в ветку `test`. В ней собираем
APK и проверяем изменения. После подтверждения результатов создаём Pull request
из `test` в `master`. Напрямую новые изменения в `master` не отправляем.

## Перед сборкой

1. Проверить рабочую ветку, состав изменений и адрес Apps Script.
2. Обновить документацию, если менялись процессы, запросы или схема.
3. Прогнать локальный набор:

```powershell
.\scripts\Test-Api.ps1 -JavaHome 'D:\Android Studio\jbr'
```

После изменения сервера отдельно запустить проверку чтения живого развертывания
из [реестра API](api-endpoints.md). Наличие успешного локального теста не
подтверждает правильность Script Properties и публикации.

## Debug и release

Последние APK для ручного тестирования собирались как `debug`. Для сборки:

```powershell
$env:JAVA_HOME = 'D:\Android Studio\jbr'
.\gradlew.bat :app:assembleDebug
```

Результат: `app/build/outputs/apk/debug/app-debug.apk`.

При измерении размера после массовой замены изображений нужна чистая сборка:

```powershell
.\gradlew.bat :app:clean :app:assembleDebug
```

Для release используется `:app:assembleRelease`. Подпись берётся из локального
`release-signing.properties` со свойствами `storeFile`, `storePassword`,
`keyAlias`, `keyPassword`. Ключ хранится вне Git; файл настроек также игнорируется.
Результат подписанной release-сборки: `app/build/outputs/apk/release/app-release.apk`.

CI передаёт подпись через переменные `COFFEEPOINT_SIGNING_STORE_FILE`,
`COFFEEPOINT_SIGNING_STORE_PASSWORD`, `COFFEEPOINT_SIGNING_KEY_ALIAS`,
`COFFEEPOINT_SIGNING_KEY_PASSWORD`; они имеют приоритет над локальным файлом.
Без этих переменных прежняя локальная конфигурация подписи не меняется.

Ключ подписи нужно сохранять между выпусками. Debug и release с разными
ключами не устанавливаются друг поверх друга как одно обновление. До перехода
на постоянную release-подпись нужно учитывать уже установленные debug-сборки
и их неотправленные локальные данные.

Оптимизация кода release пока отключена (`isMinifyEnabled=false`);
R8/resource shrinking не входят в выполненную оптимизацию изображений.

## Изображения

17 растровых иконок в `drawable-nodpi` имеют размер 256×256 и формат WebP
с прозрачностью. Схема кнопок `grind_control_keypad` сохранена в 1448×1086,
WebP без потерь. В ссылках `R.drawable` расширение файла не используется.

Проверенная чистая debug-сборка после этих изменений уменьшилась с 42,7 до
24,4 МиБ. Это измерение конкретной сборки, а не гарантированный размер будущих
версий. Высокодетальные исходные PNG доступны в истории Git до замены ресурсов.

## GitHub Releases

Настроен [Production release](../.github/workflows/release.yml), запускаемый
вручную. Чтобы он появился в обычном меню Actions, workflow сначала нужно
слить из `test` в основную ветку `master`. Сам push в `test` рабочий релиз не создаёт.

1. Согласовать новую версию, увеличить `versionCode` и изменить `versionName`
   в Gradle, выполнить `node scripts/docs.cjs --write`.
2. Проверить `test`, затем после подтверждения слить PR в `master`.
3. Создать и отправить новый тег `v<versionName>` на проверенном коммите `master`.
   Тег должен существовать до запуска; workflow не создаёт и не передвигает теги.
4. Открыть **Actions → Production release → Run workflow**. Выбрать `master`,
   указать тег. По умолчанию `publish=false`: будет создан черновик релиза.
5. Проверить результат и описание в Releases, затем опубликовать черновик.
   Либо при запуске явно задать `publish=true`, чтобы workflow опубликовал
   новый релиз после успешных проверок и загрузки обоих файлов.

В релиз прикладываются `CoffeePoint-<versionName>.apk` и `update.json`.
Описание генерируется из GitHub release notes и требует проверки человеком.
Существующий релиз, включая черновик, не перезаписывается. Если загрузка
прервалась после создания черновика, сначала разберите причину и содержимое
черновика; повторный запуск не будет молча заменять его assets.

Текущие `v1.0.14`/`v1.0.15` уже опубликованы вручную. Новая автоматизация
не меняет их APK и не добавляет задним числом манифест к старому выпуску.
При проверке 21.10.2026 у APK из `v1.0.15` обнаружены внутренние значения
`versionName=1.0.14`, `versionCode=14`. Для нового выпуска нужен новый тег,
новая согласованная версия исходников и повторная сборка; старый тег не передвигать.

### Подпись и проверки

По решению пользователя сохраняется подпись существующих установок: используется
сохранённый локальный debug-ключ, которым подписан последний опубликованный APK,
но собирается вариант `release`, без CI applicationId и тестовых настроек.
Это выбранная совместимость, а не новый ключ. Отдельный RuStore release-ключ
имеет другую подпись и для этого канала автоматически не подставляется.

Публичный отпечаток сертификата зафиксирован в
[config/release-signing.json](../config/release-signing.json); приватного ключа
и паролей в этом файле нет. В GitHub Secrets настроены:
`RELEASE_KEYSTORE_BASE64`, `RELEASE_STORE_PASSWORD`, `RELEASE_KEY_ALIAS`,
`RELEASE_KEY_PASSWORD`. Их значения не выводятся в логи. Ключ восстанавливается
только во временной папке runner и не входит в artifacts.
Локальная резервная копия этого же ключа находится в игнорируемом файле
`keystores/coffeepoint-github-compatible.jks`. Не перегенерировать его вместе
с временным debug-ключом Studio; переход на другой сертификат требует отдельного плана.

Workflow проверяет:

- Запуск из `master`, стабильный тег и его принадлежность истории `master`.
- Отсутствие релиза с таким тегом, актуальность документации и серверные тесты.
- Android unit-тесты CI-конфигурации и обычной конфигурации.
- Подпись нового APK через `apksigner` и совпадение с зафиксированным
  сертификатом и фактическим APK последнего опубликованного релиза.
- Соответствие имени версии тегу и `versionCode`/applicationId реальному APK;
  `versionCode` должен быть строго больше, чем у последнего опубликованного APK.
- SHA-256 и размер файла перед прикреплением к релизу.

Для сравнения нужен ровно один APK в последнем стабильном GitHub Release.
Права записи GitHub выдаются только отдельному job публикации. Сборочный job
не создаёт релизы и не имеет права записи в репозиторий.

### Манифест обновления

[prepare-release.cjs](../scripts/prepare-release.cjs) формирует `update.json`
из проверенного APK, а не из вручную введённых номера версии и ссылки.
Контракт: `schemaVersion`, `applicationId`, `versionCode`, `versionName`,
`minSdk`, `apkName`, `apkUrl`, `apkSize`, `sha256`, `signingCertificateSha256`,
`sourceCommit`, `releaseUrl`. Ссылка на APK привязана к конкретному тегу;
приватные токены в манифест не добавляются.

Репозиторий сейчас приватный. Публикация assets внутри GitHub не делает их
доступными анонимному Android-клиенту. Перед внедрением проверки обновлений
нужно выбрать отдельный публичный канал метаданных/скачивания либо серверную
выдачу файлов. Личный GitHub-токен нельзя вшивать в APK. Проверка обновлений
при входе и запуск установщика в приложении пока не реализованы.

Ветка двигается с новыми коммитами, тег фиксирует версию исходников. APK
не добавляем обычным файлом в Git: он прикрепляется к релизу.

GitHub Actions проверяет актуальность версии в документации и локальные ссылки
при push в `test`/`master` и в Pull request в эти ветки. Тестовые сборки описаны
ниже. Для рабочего APK подготовлен workflow выше; его первый запуск требует
слияния в `master` и нового согласованного тега. Встроенного автообновления нет.

## Автоматическая тестовая сборка

[Android CI](../.github/workflows/android-ci.yml) запускается при push в `test`,
при Pull request в `master`/`test` и вручную через Actions. Он выполняет:

1. Контрактные тесты Apps Script на таблицах в памяти, без запросов к серверу.
2. Android unit-тесты с локальным MockWebServer, без эмулятора.
3. Сборку debug APK с параметром `-PciBuild=true`.
4. Загрузку APK, `build-info.json` и отчётов Android-тестов в artifacts на 14 дней.

Окружение CI: Ubuntu 24.04, JDK 21, Node.js 22, пакет SDK `platforms;android-37.0`, Build Tools
36.0.0 и Gradle Wrapper проекта. Локальные `local.properties`, ключ release
и `release-signing.properties` не требуются. Workflow имеет только доступ
на чтение репозитория; сервер, Google Sheets, GitHub Releases и теги не меняет.

Скачать: **GitHub → Actions → Android CI → успешный запуск → Artifacts →
CoffeePoint-ci-…**. В архиве находятся APK и сведения о версии, коммите и SHA-256.
Для PR коммит может быть тестовым merge-коммитом GitHub, а не вершиной `test`.
APK загружается только после успешных серверных и Android-тестов и сборки;
статус проверки документации нужно проверять отдельно.

У CI APK отдельный applicationId `ru.coffeepoint.ci` и суффикс версии `-ci`.
Его можно установить рядом с рабочим приложением: локальные БД раздельные.
URL и токен задаются только через `TEST_SHEETS_WEB_APP_URL` (GitHub Variable)
и `TEST_SHEETS_SYNC_TOKEN` (GitHub Secret). Без них синхронизация отключена;
рабочий URL по умолчанию не используется. Команды управления терминалами
Vendista заблокированы. Подготовка отдельного сервера и настройка сборки
описаны в [тестовом стенде](test-environment.md). Проверки workflow реальные
данные не изменяют.

Используется временный debug-ключ runner, поэтому APK из разных запусков
может не обновлять предыдущий CI APK. Не удаляйте предыдущую CI-установку,
пока в ней есть неотправленные данные. Это не канал обновления для сотрудника;
постоянная подпись и автоматическая публикация рабочих релизов — следующий этап.

Локально повторить Android-часть можно так:

```powershell
.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug -PciBuild=true
```

Обычная сборка без `-PciBuild=true` сохраняет прежний applicationId.
Чтобы запретить слияние при ошибках, сделайте проверки `Apps Script contract tests`,
`Android unit tests and test APK` и `Version and local links` обязательными
в правилах защиты `master`. Наличие workflow само по себе слияние не блокирует.

## Apps Script выпускается отдельно

Для обновления кода HTTP API сохранить файлы в нужном проекте Google и выбрать
**Развернуть → Управление развертываниями → карандаш → Новая версия**.
Обновление существующего развертывания сохраняет URL. Если создан новый URL,
его нужно перенести в Android-конфиг и пересобрать приложение.

Триггеры работают с сохранённым кодом проекта; наличие нового кода в редакторе
само по себе не обновляет опубликованный versioned `/exec`. После изменения
имени или расписания триггера проверить установленный триггер отдельно.
