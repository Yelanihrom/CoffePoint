# Основные процессы

Описание соответствует исходникам на 20.10.2026. Сетевые детали и ограничения
перечислены на страницах [синхронизации](synchronization.md) и
[известных ограничений](known-limitations.md).

## Роли

| Роль | Основные задачи |
| --- | --- |
| Оператор (`OPERATOR`) | Заправка станции, просмотр состояния и своего заработка |
| Снабженец (`SUPPLY_OPERATOR`) | Пополнение запасов станций/склада, контроль помола, обслуживание миксеров |
| Управляющий (`MANAGER`) | Оба рабочих сценария, настройки, каталог, привязки сотрудников, выплаты и команды терминалу |

Главное меню Управляющего содержит пять разделов: «Оператор», «Снабженец»,
«Аналитика», «Каталог закупок», «Настройки». В настройках доступны локальные
переключатели уведомлений по ролям и узлам; подробнее в
[синхронизации](synchronization.md#уведомления). Иконка каталога из верхней панели списка станций
снабженца удалена, в том числе в режиме Управляющего. Быстрый просмотр каталожной
позиции по нажатию на расходник остаётся доступен.
Управляющий выбирает представление оператора или снабженца через главное меню.
Роль управляющего при этом сохраняется.

В главном меню Управляющего «Аналитика» открывает два подраздела: «Продажи» и
«История обслуживаний». «Продажи» — общий итог продаж и продажи
по каждой станции за период. По умолчанию — с первого числа текущего месяца
в 00:00 по Москве по текущий момент (конечная дата не задана).
Можно выбрать обе даты; отдельной кнопки сброса даты окончания нет. Первое открытие загружает
отчёт; после изменения дат нужно нажать «Обновить продажи». Пока идёт запрос,
изменение периода и повторная загрузка заблокированы. При ошибке не показывается
нулевой или частичный отчёт. Станция без терминала помечается «Нет терминала».
Данные получает только Apps Script из Vendista: новые записи в Room/Sheets
не создаются, продажи после заправки и начисления сотрудникам не меняются.
Для Оператора и Снабженца этот экран недоступен.

«История обслуживаний» показывает записи `station_service_visits` за свой период, сначала
новые: станцию и адрес, сотрудника, дату и время завершения 4-го этапа по Москве.
По умолчанию период — с первого числа текущего месяца по текущий день.
Поля «С / По» оформлены как в продажах. Обе даты включаются целиком по Москве;
смена даты сразу фильтрует локальный список без сетевого запроса. При обратном
периоде показывается ошибка, а не список. Выбранный период сохраняется при обновлении.
Список наблюдает Room и обновляется после импорта и локальных изменений.
При открытии и по иконке обновления используется существующий импорт сотрудников,
операций и визитов; при ошибке остаётся история устройства. Pending-визиты тоже
видны, с отметкой ожидания или ошибки отправки. Отсутствующие справочники не
скрывают визит: вместо имени показывается ID. Новых действий записи и начисления
этот экран не добавляет. Выбор периода в подразделе «Продажи» на историю не влияет.
Оба подраздела доступны только Управляющему. Схема БД и серверный контракт не менялись.

## Заправка оператором

Перед открытием первого шага кнопка запуска обновляет выбранную станцию и её
остатки одним запросом. Склада в операторском запросе нет, в том числе у
управляющего. При ошибке можно повторить, отменить или явно продолжить локально.

1. Открыть станцию и нажать «Начать заправку».
2. На первом шаге указать фактические остатки и перейти далее. Локальные остатки
   сохраняет `ServiceStep1ViewModel`; этот шаг не завершает заправку станции.
3. На втором шаге выполнить обязательный чек-лист.
4. Завершение сохраняет локально дату заправки и обнуляет продажи после заправки,
   затем выполняет прямую отправку.
5. Для `coffee_station` используется `complete_service`: только
   `id,lastServiceDate,salesAfterService,salesUpdatedAt`. Остатки отправляются
   отдельно, если они ещё не синхронизированы.

Фотографии не входят в условие завершения. Модуль камеры, модели и маршрут
сохранены для будущего возвращения функции.

## Обслуживание снабженцем

Перед первым шагом обновляются выбранная станция, её остатки и склад.
Это относится и к управляющему при выборе «Начать обслуживание».
Настройки станции используются локальные. Подробности — в [синхронизации](synchronization.md).

1. **Пополнение запасов.** На первом шаге выбрать общий источник
   «Склад» / «Сторонняя закупка» и указать, сколько действительно добавлено.
   Значения предзаполнены как `max(максимум − остаток в системе, 0)`.
   Счётчики показывают только количество добавленного, без остатка склада.
   Доступность склада проверяется: нехватка подсвечивается и блокирует переход.
   Источник выбирается на экране, без модалки.
2. **Проверка остатков.** Кнопка «Проверить остатки» открывает шаг 2 из 4.
   Ожидаемый итог равен исходному остатку плюс добавленное.
   Под заголовком выделен цветной блок «Проверить и указать фактические остатки
   после пополнения» с увеличенным шрифтом. У пополненной позиции показано
   зелёная строка «Пополнено: количество» и ниже корректировка при наличии. Для нулевого
   пополнения подпись скрыта, но сама позиция доступна для корректировки.
   Ожидаемый итог и строка источника на шаге проверки не выводятся.
   Снабженец корректирует итог по факту. Исправление итога не меняет добавленное
   количество и списание. При возврате ручная корректировка сохраняется;
   изменение добавленного после неё не пересчитывает итог молча.
   По кнопке «Далее» фактические остатки станции и списание добавленного товара
   со склада сохраняются одной Room-транзакцией. Доступность склада повторно
   проверяется в ней: при нехватке не записывается ни станция, ни склад.
   «Сторонняя закупка» не меняет склад. Затем идут прежние отдельные HTTP-запросы
   абсолютных значений и очередь повторной отправки. Пример: исходно 4, добавлено 8,
   фактический итог исправлен на 11 — станция получает 11, склад уменьшается на 8.
3. **Контроль помола.** Выполнить инструкцию и подтвердить проверку. Нормальный
   диапазон на шкале — 3–6 импульсов/с; вне него показана инструкция регулировки.
4. **Обслуживание узлов** — обязательный четвёртый шаг. Миксеры включаются всегда,
   независимо от даты предыдущего обслуживания. Контейнер жидких отходов
   исключён из процесса снабженца. Чек-лист состоит из двух обязательных пунктов:
   «Помыть миксеры», «Общий тест системы». Очистка/продувка УЗК исключена.
   Общий тест содержит ненумерованную подсказку:
   зажать кнопку датчика закрытия двери в верхнем углу дверцы; УЗК не должен
   скрипеть, вода должна поступать в каждый миксер, на экране не должно быть ошибок.
   Эти три условия идут после
   жирного подзаголовка «Критерий проверки:». Раскрывающийся текст снабженца
   выровнен по левому краю строки с чекбоксом. Предупреждение про
   силиконовые шланги относится только к миксерам.
   Завершение доступно после отметки обоих пунктов;
   обновляется только дата обслуживания миксеров, даты контейнера и ТО УЗК не меняются.
   Для роли Снабженца одновременно сохраняется локальный визит
   на единственного активного снабженца: UUID, станция, сотрудник и время завершения. Повтор отправки
   использует существующий визит; Управляющему визит не записывается.
   Каждый новый визит атомарно создаёт локальное начисление 2000 рублей.
   Повтор с тем же UUID не начисляет деньги снова. Android отправляет
   `complete_supply_visit`; серверное подтверждение заменяет предварительное
   начисление. Непереданные прежние локальные визиты тоже отправляются с теми же ID.
   Без сети визит сохраняется для общего воркера исходящей синхронизации.
   Управляющий обновляет дату миксеров без визита и начисления;
   операторская заправка не меняется. В снабженческих списках контейнер
   не показывается. По умолчанию уведомления о сроках миксеров/контейнера
   получает только управляющий; снабженцу включены только критичные остатки
   станций. Склад и отдельные узлы включаются в локальных настройках уведомлений.
   Управляющему оставлены карточка
   контейнера с ручной сменой даты и уведомления о его просрочке через 180 дней.

Снабженческий `complete_service` изменяет только `mixersServiceDate`.
Он не изменяет `liquidWasteContainerServiceDate`, не сбрасывает продажи
и не изменяет дату заправки оператора.

После локального сохранения редактирование снабженческого ввода заблокировано.
При ошибке отправки кнопка «Продолжить» в диалоге позволяет перейти к контролю
помола с уже сохранёнными локальными остатками.
При повторной отправке в рамках текущей ViewModel склад не списывается второй
раз: повтор отправляет уже сохранённые значения. Флаг этого действия хранится
в памяти ViewModel; устойчивой операции списания с отдельным ID в БД пока нет.
Перемещения между станциями не реализованы.

Интервалы обслуживания узлов отсчитываются от последней даты: миксеры — 30 дней,
контейнер жидких отходов — 180, УЗК — 180, расширительный бачок — 360,
вытяжка и кофемолка — 720. В день наступления срока узел требует обслуживания;
при пустой дате срок не определяется.

## Склад и поставка

В снабженческом списке (включая режим Управляющего) фильтр «Все станции»
показывает все станции, даже без нехватки запасов и просроченного ТО.
При отсутствии позиций к пополнению карточка показывает «Станция полностью
загружена» без заголовка закупки. Исключённые из снабжения станции отмечены
отдельно: «Станция исключена из снабжения». Фильтры «Половина» и «Критично»
по-прежнему отбирают станции по остаткам, не скрывая остальные позиции внутри
карточки. Потребность в пополнении показывается отдельно для каждой станции.

Склад хранит девять позиций: стаканы, крышки, сахар, мешалки, пакеты, кофе,
молоко, шоколад и топпинг. Управляющий задаёт минимум и максимум.

При настроенных положительных минимумах и максимумах:

- Меньше минимума — критично.
- От минимума до середины `(min + max) / 2`, не включая середину — предупреждение.
- От середины и выше — нормальный остаток.

Нулевой предел означает ненастроенное правило; точные условия отдельных
экранов задаются их моделями. Для уведомления склада обязательно должны быть
положительными оба предела.

Сводная плашка «К поставке» удалена: снабженец планирует отдельные визиты,
а не общий маршрут по всем станциям. Плашка «Склад» сохранена.
`excludeFromSupplyPlanning` исключает станцию из планирования. Фильтры
«Все станции», «Половина», «Критично» отбирают только станции: «Половина» —
есть хотя бы одна предупреждающая или критичная позиция, «Критично» — хотя бы
одна критичная. В карточке выбранной станции показываются все позиции к поставке,
без фильтрации по цвету, с количеством до максимума этой станции.
Правило одинаково для Снабженца и режима снабжения Управляющего.

## Каталог закупок

Позиции группируются по `itemType`, варианты сортируются с учётом приоритета.
Управляющий видит неактивные варианты и элементы редактирования. Остальные роли
видят активные варианты. Краткая информация по нажатию на иконку содержит
название позиции, артикул и цену. При наличии ссылки можно открыть магазин
из каталога. Сохранение каталога выполняется напрямую, без фонового воркера.

Удаление присутствует в Android, но отсутствует в текущем локальном серверном
роутере: см. [ограничения](known-limitations.md).

## Начисления, выплаты и взаиморасчёт

Apps Script примерно в 02:00 по Москве запрашивает продажи за вчерашний день.
Для активного оператора учитываются его действующие привязки к станциям и
флаг `excludeFromOperatorEarnings`. Ставка в серверном коде — 15 рублей за продажу.
Сервер сохраняет `EARNING` с ID `AUTO-EARNING-{employeeId}-{date}`.

Управляющий вводит сумму и выполняет выплату. Android создаёт отдельную
операцию `PAYMENT` с собственным ID и отправляет её через синхронизацию сотрудников.

История фильтруется по `operationDate` за выбранный период, по умолчанию за
последние семь дней. Взаиморасчёт от этого периода не зависит:

```text
Взаиморасчёт = все начисления сотрудника - все выплаты сотруднику
```

Положительный остаток обозначает ожидаемую выплату, отрицательный — выданный
аванс. Ручная кнопка начисления удалена. Текущий день появится в начислениях
после следующего ежедневного запуска; автоматического почасового начисления нет.

Экран заработка доступен снабженцу через иконку денег, а управляющему —
из режима снабжения. Он показывает начисления снабженца за завершённые визиты и
его выплаты из Room, при открытии загружая актуальную историю из Sheets.
Управляющий может записывать выплаты: они сначала сохраняются на устройстве,
затем отправляются с постоянным UUID. Снабженец только просматривает историю.
Взаиморасчёт использует ту же формулу, включая предварительные локальные записи.
Дата начала работы на экране снабженца скрыта. Предвыбранный период истории —
последние семь дней включительно по Москве, как у оператора; это не дата начала работы.
Для выплаты Денису Управляющий открывает заработок из режима снабжения,
вводит сумму в блоке взаиморасчёта и нажимает «Выплатить».
Выбор отдельного сотрудника при входе ещё не реализован: для оператора выбирается
первый активный `OPERATOR`, для снабженца — единственный активный
`SUPPLY_OPERATOR`. Production требует серверного сотрудника, а не local-only
профиля. Сервер опубликован 14.11.2026 как версия 27; выпуск APK ещё предстоит.
Автоматические начисления Максима не изменены.
