# CoffeePoint: инструкции для агента

## Начало работы

- Сначала проверь рабочую ветку и незакоммиченные изменения. Новые изменения
  делай в `test`; не отправляй их напрямую в `master`. Слияние, тег и рабочий
  релиз требуют подтверждения пользователя. Не откатывай чужие изменения.
- Перед правкой прочитай соответствующий код и документ из карты ниже.
  Документация помогает найти контекст, но при расхождении проверяй реализацию
  и исправляй описание. Не считай историю чата единственным источником требований.
- Отвечай пользователю по-русски. Документы и пользовательский текст сохраняй
  в UTF-8, проверяй кириллицу после изменения строк.

## Повторное использование UI

- Перед созданием UI-элемента проверь [каталог UI-kit](docs/ui-kit.md),
  `shared/component` и аналогичный элемент на существующих экранах.
- Используй готовый компонент. Если аналог пока приватный внутри экрана,
  вынеси его в `shared/component` и подключи в старом и новом месте, не копируй.
- Если возможностей не хватает, расширяй API общего компонента с сохранением
  текущего вида по умолчанию. Новый вариант дизайна требует явной задачи.
- Для выбора периода используй `AppPeriodSelector`, для отдельного поля —
  `AppPeriodDateField`. Правила дат, запросы и состояние остаются в feature.
- При добавлении общего компонента обновляй каталог UI-kit и его тесты.
- Явные загрузки/сохранения на активном экране показывай через общий
  `SyncSendingOverlay` с блокировкой взаимодействий. Не создавай частные
  индикаторы; фоновые воркеры и локальная фильтрация экран не блокируют.

## Что нельзя случайно изменить

- Продажи и ежедневные начисления получает Apps Script. Не возвращай запросы
  продаж в Android. Прямой Vendista-клиент оставлен для команд терминалу;
  в CI-сборке эти команды намеренно заблокированы.
- Аналитика — отдельный read-only запрос `sales_analytics` через connector:
  по умолчанию с первого числа месяца по Москве, без `endDate`/Vendista `DateTo`.
  Не подменяй отчёт значением `salesAfterService` и не записывай его в Room.
  Перед выпуском проверяй поддержку метода именно рабочим развертыванием:
  работоспособность тестового deployment не подтверждает рабочий сервер.
  Вход — `AnalyticsMenuScreen`: «Продажи» и «История обслуживаний». История читает
  `StationServiceVisitDao.observeHistory()` с именами станции/сотрудника, включает
  pending-визиты и обновляется существующим импортом сотрудников, не запросом продаж.
- Завершение заправки оператора отправляет узкий набор полей станции через
  `complete_service`. Снабженец обновляет только выбранные узлы обслуживания.
  Не заменяй эти операции общим upsert строки и не сбрасывай продажи снабженцем.
- В `SheetsRepository.gs` русские даты разбираются явно до `new Date`;
  нормализация миллисекунд применяется только к ISO-времени, не к году.
  Не возвращай ложные конфликты дат обслуживания 1–12-го числа. После смены
  production URL нужен новый APK; обновление прежнего deployment сохраняет URL.
  Проверки и порядок публикации — в [серверной документации](google-apps-script/README.md).
- В снабженческом последнем шаге обязательны две задачи: мытьё миксеров и общий
  тест (нет скрипа УЗК, вода в каждом миксере, нет ошибок на экране).
  Очистка УЗК в чек-лист не входит; дата полного ТО УЗК не меняется. Зелёная зона
  контроля помола — 3–6. Для раскрытий используй существующий `ChecklistRow`.
- Импорт/проверка уведомлений и отправка pending-изменений — разные воркеры.
  Не дублируй отправку в импортирующем воркере.
- Интервал уведомлений задаёт `core/notification/NotificationInterval`: 6 часов
  отдельно для каждого типа на устройстве, общий для ролей и с сохранением
  времени показа в SharedPreferences. Не увеличивай ради него ежечасный интервал
  импорта. Подробности — в [синхронизации](docs/synchronization.md).
- Настройки уведомлений — `core/notification/NotificationSettings`,
  вход из главного меню Управляющего. Флаги отдельные по ролям и узлам;
  снабженцу по умолчанию включены только критичные остатки станций.
  Подключены к Sheets через `NotificationSettingsRepository`: dirty-флаги
  сохраняются локально, отправка только через исходящий воркер/репозиторий,
  импорт не стирает pending. Подготовленный production-код требует публикации
  серверного контракта до выпуска APK; текущий статус — в инструкции публикации.
  Не путай их с настройками подсветки.
- При сетевой ошибке сохраняются локальные изменения и статусы синхронизации.
  Повтор запроса не должен повторно списывать склад. Перезапуск процесса и
  конкуренция устройств пока не полностью покрыты: не обещай гарантии без тестов.
- Взаиморасчёт — все начисления минус все выплаты сотруднику; выбранный период
  истории его не ограничивает. Ручное начисление из приложения удалено.
- `station_service_visits` записываются на 4-м этапе Снабженцем:
  визит, начисление 2000 рублей и pending-дата миксеров — одна Room-транзакция, повтор использует тот же
  UUID из SavedStateHandle. Управляющему визит не записывается; суммы в визите нет.
  Подключён `complete_supply_visit`: визит и начисление
  записываются одним Sheets API batch; см. `SupplyServiceVisits.gs` и API-документ.
  Начисление связано через `sourceType/sourceId`; прежние pending-визиты
  отправляются с тем же ID, без второй финансовой операции.
  ID начисления снабженца и выплаты — обычный UUID. Не вычисляй финансовый
  ID из визита: отправляй сохранённый `earningId`, повтор ищется по источнику.
  Формат автоматических начислений оператора `AUTO-EARNING-*` не меняется.
  Экран заработка переиспользуется с отдельным профилем и кэшем снабженца.
  Контекст — [модель данных](docs/database.md).
- В тестовой БД создаётся локальный снабженец «Денис» (`isLocalOnly=true`).
  `EmployeeDataImporter` принимает серверного сотрудника только при совпадении
  ID/имени/роли, снимает локальный признак и открывает отправку выплат.
  Начисление визита никогда не отправляй общим upsert: только визит, затем
  подтверждение пары визит/операция. Pending-записи при импорте не удаляются.
  Не создавать сотрудника в Sheets автоматически и не принимать другой профиль
  при коллизии ID. Рабочая сборка не создаёт тестового сотрудника и не записывает
  визит на local-only профиль. До выпуска нужен ровно один активный серверный
  снабженец; preflight проверяет реестр сотрудников. Подробности — в модели данных.
- Модуль камеры сохранён по явному решению пользователя. Не удаляй его как легаси.

## Окружения и секреты

- Тестовая debug-сборка включается свойством `ciBuild=true` (по умолчанию
  в `gradle.properties`, эквивалент `-PciBuild=true`), имеет отдельный
  applicationId и использует только тестовый URL/токен. Не добавляй fallback
  на рабочий сервер, не ослабляй блокировку команд терминалу ради тестов.
  Локальные настройки Studio — игнорируемый `test-backend.properties`;
  генератор `scripts/configure-studio-test.cjs`. Release остаётся рабочим.
- `.codex`, ключи подписи, OAuth-файлы, токены и локальные properties не коммить.
  Не выводи секреты, полные авторизованные URL или HTTP-тела с токенами в логи.
- Для тестового сервера запускай `scripts/prepare-test-backend.cjs` или
  `scripts/Invoke-TestClasp.ps1`. Комплект генерируется в `.codex/apps-script-test`;
  не редактируй его как исходник. Правь серверный код или генератор.
- Без явной задачи на рабочее окружение не пиши в рабочую таблицу, не обновляй
  рабочее развёртывание и не устанавливай его триггеры. Перед live-записью
  проверь тестовые Script ID, deployment ID и spreadsheet ID по конфигурации.
- Доступ к рабочему Apps Script настраивается отдельно в
  `config/environments/production.json`; `Invoke-ProductionClasp.ps1` разрешает
  только проверку и скачивание. Это не публикация. Каталог снимка —
  `.codex/apps-script-production`, его не коммить и не подменять файлами test.
- `Production Apps Script` — отдельный workflow только с ручным запуском,
  по умолчанию preflight без записи. Нужны защищённый environment, Secrets,
  SHA из master и ожидаемая серверная версия. Подготовка workflow не означает
  разрешение на публикацию; учитывать исполнение триггеров на новом HEAD.
- Не запускай изменяющие live-тесты на общих данных без восстановления,
  защиты от параллельного запуска и явного понимания затронутых записей.

## Проверки

Из корня проекта, Node.js 22+:

```powershell
node --test scripts/tests/docs.test.cjs scripts/tests/test-backend.test.cjs scripts/tests/production-access.test.cjs scripts/tests/production-backend.test.cjs scripts/tests/studio-test.test.cjs scripts/tests/ui-kit.test.cjs scripts/tests/release.test.cjs google-apps-script/tests/http-contract.test.cjs google-apps-script/tests/supply-visits.test.cjs google-apps-script/tests/notification-settings.test.cjs
node scripts/docs.cjs --check

$env:JAVA_HOME = 'D:\Android Studio\jbr'
.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug -PciBuild=true --console=plain
```

Путь к JDK — пример для текущего компьютера; при другом окружении используй
доступный JDK 21. Если Node.js не в PATH, найди установленный или bundled runtime;
не считай отсутствие команды доказательством отсутствия самого runtime.
Без тестовых переменных и локального `test-backend.properties` CI APK
собирается, но не синхронизируется.

- Изменение запросов: обе стороны контракта и соответствующие JVM/Node-тесты.
- Изменение бизнес-правила: тесты границ, нулевых значений, ролей, дат и повторов
  в затронутом сценарии. Не ограничивайся успешной компиляцией.
- Изменение схемы: Room, миграции, сервер и независимый JSON-контракт
  `app/src/test/resources/contracts/sheet-schema.json`.
- Только документация: проверка ссылок/версии и тесты скрипта при его изменении;
  пересборка APK не нужна.
- В отчёте различай локальные проверки, GitHub CI, live API и ручную проверку
  интерфейса. TODO/skip не называй покрытым сценарием.

## Документация вместе с кодом

- Меняешь поведение, API, схему, расписание или сборку — обновляй соответствующие
  документы в том же PR. Исправил ограничение — скорректируй список ограничений.
- После изменения версии в Gradle выполни `node scripts/docs.cjs --write`.
  Генерируемый блок в `docs/releases.md` вручную не редактируй.
- Этот файл хранит короткие правила и навигацию, а не полный журнал работы.
  Новые подробности добавляй в профильные документы и ставь ссылки здесь,
  только если это помогает следующему агенту найти нужный контекст.
- Источники документации и исходники публикуются через `test`. Публикация Git
  не обновляет APK на устройствах или сервер Apps Script автоматически.
- Рабочие APK выпускаются через `Production release` по отдельному подтверждению
  и новому тегу `master`. Не заменяй ключ совместимости из
  `config/release-signing.json` другим локальным ключом и не перезаписывай релизы.
